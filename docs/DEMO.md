## Подготовка до выступления

1. Выполнить `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`, проверку публичных файлов.
2. Запустить `pnpm start`; убедиться, что локальный сервер доступен и аудио выбранного звонка загружено.
3. Человеку заранее проверить спорный C7 и, при необходимости, подготовить настоящую локальную ручную оценку звонка. Агентные тестовые0-балльные записи не являются оценкой качества работы.
4. Открыть исходный и изменённый снимки C9, сохранить IDs успешных реальных оценок из `private/reports/semantic-acceptance.json`. Основное выступление работает с ними без сети. Решить до старта, нужен ли опциональный живой запрос; при деградации сети не тратить окно демонстрации на цепочку повторов.
5. При наличии контрольного group_id ввести его в поле «Группа импорта» и выполнить GET. Неизвестное происхождение не разрешает внешнюю обработку автоматически. Подтверждение синтетического происхождения и разрешения Free-tier обработки делает уполномоченный человек через интерфейс; реальные звонки исключены.
6. На стоп-коде зафиксировать проверенный commit. Публикацию и отправку ссылки выполнять только после явного разрешения пользователя; никакие private-артефакты не включать.

## Честный резервный сценарий

Сеть и бесплатная квота не гарантированы. Основной вариант показывает сохранённые настоящие результаты. Если выбран опциональный новый запрос и приходит ошибка, показать её и открыть ранее сохранённую настоящую оценку соответствующей проверенной версии. Явно сказать: «Это сохранённый результат прошлого реального запроса». Не выдавать его за только что завершённый вызов и не утверждать, что неуспешная новая версия оценена. Для полной живой проверки отдельно использовать воспроизводимый browser-сценарий без лимита5минут.

Автоматизированная репетиция: `node node_modules/tsx/dist/cli.mjs scripts/rehearse-demo.ts --current-model` при запущенном сервере. Для официального результата и обеих версий C9 проверяются текущая модель, статус реального API-ответа и выбранный ID. Старые записи могут не иметь поля `origin`; это не переписывает их историю, если status/provider/mode подтверждают прежний реальный ответ.

Репетиция действительно занимает300 секунд. Десять этапов должны начаться в пределах1 с от расписания и завершиться до300 с; общая допустимая длительность — от300 до301 с. Для каждого запуска создаётся отдельный каталог `private/reports/demo-rehearsal-current-model/<runId>/` с отчётом и11 снимками, прежние отчёты сохраняются.

Используется отдельный сеанс браузера. Запросы записи и внешние браузерные запросы блокируются; обращения API выполняются только GET. Сравниваются полные сохранённые оценки/попытки/правила/история апелляции, manifest и ID человеческого раунда. Существующие человеческие записи проверяются по хэшам без изменения; новые записи команды допускаются. Пользовательская вкладка и её черновики не открываются и не очищаются.

Реплика ведущего: «Это сохранённый ответ реального запроса Gemini 3.1 Flash Lite. Во время репетиции нового вызова нет. Показанные100/100 — расчёт по ответам модели, а не доказательство смысловой точности. Предварительные риски C2/C7 требуют человеческой проверки; они не назначают gold и не меняют сохранённый результат».
